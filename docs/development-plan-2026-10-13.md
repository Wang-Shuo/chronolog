## 3. M1：修复更新可靠性

**目标：** 同一个 Vault 可以反复更新；失败不会改变已验收的内容。

**已验收：** A1–A8 回归、真实数据副本演练和 Quartz 构建通过，见[验收记录](acceptance/m1-2026-10-13.md)。下列任务已完成；日常运行与恢复方式见 [README](../README.md)。fixture 和故障演练仍使用隔离副本。

**建议拆分：** 一个实现 PR，可按范围契约、历史合并、发布门禁拆成多个提交。

### 开发任务

- [x] **M1.1 定义运行范围。** 区分 full 与 incremental，记录请求来源、成功来源、失败来源、采集模式、覆盖区间、采集时间和完整性状态。`--reconcile` 仅允许作用于成功且确认完整的来源范围；未选择、失败、截断的来源不得因“本次未出现”被标记 superseded。
- [x] **M1.2 合并历史事实。** 从 Markdown 事实库读取历史 Release/Change，按稳定 ID 合并当前批次，再分析和渲染完整的产品、主题、首页及关系。派生索引可重建；不能依赖某台机器保留的旧 `_pipeline/` JSON 才能增量运行。
- [x] **M1.3 增加采集门禁。** 首版默认任一请求来源失败则拒绝发布并返回失败状态。区分“成功但没有新内容”和“采集失败或异常空结果”。如后续支持部分成功模式，必须显式启用、保留失败来源原内容并报告降级。
- [x] **M1.4 校验后再提交写入。** Round 1 有 failed/DLQ 记录时，首版默认拒绝发布和对账，并保留诊断结果，避免将校验失败的既有卡误标 superseded；正常的 pending theme review 不算校验失败。随后在暂存 Vault 中执行渲染、Round 2 和发布集合检查；全部通过才更新正式 Vault。校验失败、机器区冲突或提交中断时保留或恢复原内容，不能只依靠最终退出码表示失败。
- [x] **M1.5 修正监控日期。** 默认使用执行日并明确时区，保留 `--today` 用于历史回放；基于合并后的历史统计沉默。来源未成功采集时，将状态记为采集异常，不把缺失数据解释为产品沉默。
- [x] **M1.6 更新操作说明。** 明确 fixture 隔离方式、完整回填与日常增量的用法、失败恢复路径、run-id 和证据存放位置。

### 必须通过的回归场景

| 编号 | 输入或操作 | 预期结果 |
| --- | --- | --- |
| A1 | 完整回填后，仅输入最近一条 Release | 历史档案仍在产品和主题索引中；全局计数及关系不缩成当前批次；Round 2 通过 |
| A2 | 相同输入重复执行 | ID、路径及内容稳定，无重复卡片；人类区域和 overrides 保留 |
| A3 | 一个来源失败 / 全部来源失败 | 默认返回失败；正式 Vault 内容摘要执行前后完全一致；报告包含失败来源和原因 |
| A4 | 来源成功但没有新增内容 | 保留现有内容，标记 no-change；不清空首页，不误报失败 |
| A5 | 仅对一个完整来源 reconcile | 只对该来源中确实被取代的记录执行对账；其他来源及待审卡片不被误废弃 |
| A6 | 截断输入、Round 1 failed/DLQ、Round 2 错误或 machine_hash 冲突 | 拒绝不完整的 reconcile；校验失败的历史卡不被误标 superseded；任何发布门禁失败都不改变正式 Vault，错误有证据可查；正常 pending 不误触发失败 |
| A7 | 在正式写入过程中注入失败 | 已发布内容可以恢复到提交前一致状态，不留下半批次输出 |
| A8 | 默认日期与显式历史日期分别运行 | 默认日期符合声明的执行时区；回放结果可重复；采集失败不产生虚假的沉默结论 |

**完成条件：** A1–A8 均有自动化测试和通过证据；现有测试与 Quartz 构建通过；临时真实数据副本至少完成一次“全量 → 增量 → 重跑 → 故障恢复”演练。仅成功生成一次页面不能关闭 M1。

**目标：** 发布范围明确，数据覆盖透明，至少有一个产品和两个主题能支撑真实研究问题。

### 开发与内容任务

- [x] **M2.1 隔离发布集合。** fixture 只用于测试；不进入真实 Vault 的公开输出。superseded 记录保留用于追溯，默认退出活动搜索、目录、图谱和统计；若提供归档访问，必须明确标记并保持历史链接可解释。
- [x] **M2.2 刷新三来源。** 在 M1 通过后采集至执行日可获得的最新内容，分别记录最后成功采集时间、最新 Release 日期、最早覆盖日期、来源 URL、快照时间和已知缺口。调查 Claude Code 的 2025-12-19 起点；无法证明更早历史完整时明确说明范围。
- [x] **M2.3 检查内容原子性。** 修复标题残片独立成卡、重复卡片和描述缺少上下文的问题；每张卡应表达可独立理解的具体变化并能回到官方证据。
- [x] **M2.4 精修一个产品叙事。** 首选 ChatGPT，阶段命名和边界由实际能力或策略转折支持，每个阶段有摘要、代表变化和来源；不以机械二等分或更换标题代替叙事。
- [x] **M2.5 精修两个主题。** 首选 `agent-mode` 与 `pricing-model`，解释各产品发生了什么、何时发生、是否为同一能力或机制。证据只支持“同主题时间先后”时，不推断采用、跟随或因果关系；保留 tracked-products-only 范围说明。
- [x] **M2.6 建立黄金样本与回归。** 按产品、时间和主题分层记录卡片及关系审核，保存来源、预期判断、失败原因和修正结果。后续规则或模型变化复用这组样本。
- [x] **M2.7 改善阅读入口。** 首页展示覆盖范围、最后成功更新和精选主题入口；产品页提供可读摘要。将 `verbosity_baseline` 等诊断信息移出主要阅读路径。
- [x] **M2.8 同步范围与进度。** 按实际验收更新 PRD 关联状态，保留三来源、规则提取与人工审核的现行选择，明确原设计未达成项。

### 验收清单

- [x] **B1 发布集合：** 检查实际 HTML、搜索索引、目录与图谱，四个 fixture 产品及其模拟内容均不在活动发布集合中；superseded 不计入活动统计；现有历史引用无新增断链。
- [x] **B2 计数一致：** 首页与产品、主题索引使用同一活动集合，并与发布索引交叉核对。验收比较本次集合，不要求更新后的数量仍等于旧基线 648 / 1,759。
- [x] **B3 覆盖可查：** 每个来源都有本次采集和覆盖证据。最后抓取时间与最新 Release 日期分开展示；上游近期无发布不能自动判为采集过期。人工导入的 ChatGPT 快照注明获取日期，不冒充当日自动采集成功。
- [x] **B4 卡片抽样：** 初版验收取 60 张卡，每产品 20 张，覆盖早期、近期及不同主题。全部可追溯官方证据、无捏造变化，至少 55 张同时通过“主题正确、事件可独立理解、无明显重复”的人工判定；修正后重跑固定样本，并额外记录发现的系统性问题。
- [x] **B5 关系抽样：** 从 `evolves_from` 和跨产品关联中选取共 20 个案例，包含仅主题相近的反例；语义关系必须有相应证据，纯时间先后不得标为能力跟随。黄金样本中的不支持关系应被移除或降为明确的时间关联。
- [x] **B6 叙事验收：** 一个产品、两个主题的审核记录能回答“发生了什么转折、证据在哪里、哪些结论仍不确定”；主题时间线在浏览器可读、可导航，不能只凭静态构建通过验收。
- [x] **B7 回归：** 黄金样本检查、全 Vault 链接校验和 Quartz 构建通过。

60 张卡和 20 个关系案例是本计划的初版验收样本规模，主题正确率门槛与 PRD 的 >90% 方向一致；它们不构成总体准确率的统计保证。需要调整口径时，先在验收记录中说明原因和新口径，再执行评测，不能为让结果通过而事后改阈值。

**完成条件：** B1–B7 全部附证据。此时可以认定“三来源 MVP 的内容价值验收通过”；原计划的 5–8 产品、每产品两年纵深等目标须单独标记范围差异，不能一并宣称完成。
