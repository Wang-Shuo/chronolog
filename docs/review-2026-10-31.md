## 0. 结论

工程可靠性做得很扎实，甚至超出当前阶段的需要。但读者价值的三根支柱——**分类准确、卡片可读、有洞察**——还没有立住。站点目前更像“结构化的 changelog 镜像”，PRD 里的差异化（信号层、沉默与改稿观察、跨产品对比）尚未出现。自动运营闭环实际没有转起来，也没有任何读者数据。

下一阶段建议把投入从“证明管线可靠”转到两件事：**让内容值得读**，**验证有人读**。

| 指标 | 现状 |
| --- | --- |
| 主题分类准确率（抽样 90 张） | 严格 64%，宽松 74%；PRD 目标 ≥ 90% |
| 标题以“…”截断 | 24.6%（Claude Code 独立卡 57%） |
| 定时生成（10-15 至 10-30） | 16 次中 14 次失败，无任何通知 |
| 滚动 PR | 4 个中 2 个合并（#5、#18），2 个关闭（#19、#23） |
| 读者信号 | 站点 `analytics: null`；仓库 0 个 issue；近 14 天仓库页 2 个独立访客 |
| 投入结构 | 文档 1.04 万行 + 307 个验收证据文件；Python 代码 7,632 行 |

**值得保留：** 暂存 → 校验 → 事务发布 → 回滚的链路与 A1–A8 回归；抽取完全确定；CI 按 job 最小权限、无 `pull_request_target`、部署前确认最终 head 已人工批准；叙事在认识论上克制（抽查 12 处事实全部有原文支持）；产品页顶部（定位、节奏面板、Era）已经可读。

## 1. 产品设计

### P1【高】产品组合不自洽

ChatGPT 是消费级助手，Claude Code 与 Cursor 是开发工具，主题对比因此很难成立：Agent Mode 2026 年 209 条中 Claude Code 125、Cursor 81、ChatGPT 3；Image Generation 17 张中 16 张来自 ChatGPT。ChatGPT 也是最贵、最脆弱的来源：24 个 PR 中有 6 个（#4、#17、#20、#21、#22、#24）在处理它的采集（403、快照过期、浏览器抓取、客服组件误入）。

建议二选一：

- **聚焦“AI 编程代理”（推荐）**：保留 Claude Code、Cursor，加入 Codex CLI、Gemini CLI（GitHub Releases）与 GitHub Copilot（官方 changelog）。均为 PRD 定义的 tier-1 来源，也是 PRD 第 13 节原本建议的方向。候选来源的覆盖与历史深度需先核实。
- **保留 ChatGPT**：补齐同类产品（Claude 应用、Gemini 应用），分“助手”“编程”两条赛道，主题对比只在赛道内进行。

### P2【高】差异化能力未落地，先做低成本版本

L1 信号、弱信号观察站、改稿检测、跨产品对比视图均未实现（`collect.py` 中没有改稿检测，`Alerts/` 为空）。

- **每周信号页**：规则先挑 launch / pricing / policy / 新模型 / 弃用类卡片，人工每条补一句“为什么重要”，替换首页 Latest changes。
- **能力矩阵**：行是能力（后台代理、子代理、MCP、记忆、计划模式……），列是产品，单元格是首次公告日期并链接卡片；约 30 行，人工策展。
- **改稿检测**：release 原文按 sha 入库（见 4.2），diff 出“谁悄悄改了已发布的说明”，同时解决卡片链接失效与 ChatGPT 覆盖门禁误判。

### P3【高】计量口径混乱，Claude Code 的写法压倒一切

- 首页 “2,751 tracked changes” 是卡片数，这些卡共引用约 5,100 行原文；Release 页 “9 tracked changes across 8 themes” 的 9 张卡里有 21 行变更；摘要卡标题 “7 Apps and Integrations changes” 用的又是行数。
- Claude Code 占比：Safety and Privacy 191 张中 149 张；2026-09 归档 295 条中约 78%；RSS 最新 24 条中 22 条来自它的两个版本。
- 建议：全站统一“卡片（公告级）”与“条目（行级）”两个单位；引入 highlight / routine 两级重要性，首页、主题时间线、RSS、关键节点只显示 highlight。

### P4【中】首页与导航

- **Latest changes** 按日期取每个产品最新 6 张，不看重要性：Claude Code 6 条中 5 条是 “2 Agent Mode changes in v2.1.316” 一类摘要卡；Cursor 6 条全部来自同一篇 Agent SDK 公告，含两条近乎重复（“generally available” 与 “available”）及脱离上下文的 “Evals”“Channels”；ChatGPT 6 条中 4 条主题分错或只是说明句。
- **Start exploring** 只列 2 个主题，而已有 7 个主题写了研究摘要。
- **左侧导航**：48 个月份按字母排序（April 2023, April 2024…），所有文件夹默认展开，近 80 项。
- **主题页**：25 页中 23 页向读者显示维护提示 “Auto-selected; edit `key_moments` in editorial.yaml to curate.”；全量时间线不折叠，agent-mode 在手机上 23 屏；图谱成团，Backlinks 数百条。
- 面包屑链到 557 KB 的文件夹列表页（`Changes/Claude-Code/` 1,422 项）；`#index`、`#moc` 等标签对读者可见。

### P5【中】缺少面向研究者的能力

发布 `cards.csv` / `cards.json`（日期、产品、主题、kind、标题、链接、引文），主题页支持按产品筛选。

### P6【高】没有验证闭环

`quartz.config.ts` 中 `analytics: null`，PRD 第 16 节 KPI 无法测量；“Report an issue with this card” 从未收到 issue；仓库没有描述与主页链接。建议加隐私友好的统计（GoatCounter、Cloudflare Web Analytics 等），找 5–10 位目标读者做“3 分钟内找到一个趋势”的测试（PRD Phase 3 成功标准）；拿到反馈前不开新的工程里程碑。

### P7【中】版权与合规

卡片基本整段、整条照搬原文，相当于全文转载三家的 changelog，而 PRD 风险表的对策是“短引文 + 中性转述 + 原文链接”。叠加 5.2 的浏览器抓取与把整页 HTML 提交到公开仓库，风险会累积。建议引文收到一到两句，证据只留哈希。（非法律意见，条款适用性未核实。）

## 2. 内容设计

### C1【高】分类准确率 64–74%，根因是关键词打分

抽样 90 张：严格 58/90，宽松 67/90（ChatGPT 18/30、Claude Code 18/30、Cursor 22/30，严格口径）。典型误分（均已复核）：

| 卡片 | 当前主题 | 原因 | 应为 |
| --- | --- | --- | --- |
| Claude Code 2026-04-09 “Fixed false Bash permission prompts…” | Pricing Model | 引文 `awk '{print $1}'` 命中 `\$\d`（`_scripts/extract.py:659`） | Safety（权限） |
| Claude Code “Improved the embedded grep…” | Memory and Personalization | “exhausting memory” | Reliability and Performance |
| Cursor 2025-10-29 “Increased default memory for TypeScript language server” | Memory and Personalization | memory 指内存 | Reliability and Performance |
| ChatGPT 2026-10-30 “Account switching on iOS and Android” | Memory and Personalization | “keeps its own chats, memory…” | Account and Access |
| ChatGPT 2026-10-28 “Texting your dot” | Safety and Privacy | “safely and securely” | Agent Mode |
| Claude Code 2026-04-16 auto mode for Max | Model Support | 句中提到模型 | Agent Mode |
| Cursor 2026-05-18 “Composer 2.5 is now available” | Agent Mode | — | Model Support |
| Claude Code v2.1.316 “Claude apps gateway” 多条 | Apps and Integrations | 别名 `apps` | Enterprise and Administration |

黄金样本（55/56）测的是“前后一致”，不是“分类正确”。每遇到一次误判就加一条特例正则（例如 `RESOURCE_MEMORY_RE`），是打地鼠。

建议：

1. 先修三条规则：价格匹配要求货币上下文且不看代码片段；套餐名、平台名不参与打分；Claude Code / Cursor 中的 memory 只在“产品记忆”语境下计分。
2. 把已在使用的“Codex 语义审核”正式化：LLM 作为**离线提议者**为新条目分类（输出限定为词表枚举），结果按（line_id、prompt 版本、模型）写入提交到仓库的缓存文件并在 PR 中审核；日常管线只读缓存，缺失时回退规则，可复现性不变。
3. 每月盲抽 100 张做准确率门禁（≥ 90%）。
4. 执行 C6 词表修订（拆出 permissions-sandboxing，合并或暂缓 1–5 张卡的小主题）。

### C2【高】重要性倒挂

- 大事埋在摘要卡里：Era 分界事件 “Added Claude Mods” 在 `Changes/Claude Code/2026-10-01-11-apps-and-integrations-changes-in-v2-1-287.md`；“Opus 5.5 成为默认模型” 在 “5 Model Support changes in v2.1.280”。Claude Code 约 94% 的独立卡只是因为该主题在该版本恰好只有一行（内容审计统计）。
- 碎片单独成卡：ChatGPT Go 的 “Longer memory for more personalized responses” 重复成卡 6 次；“Standard: $0.50/M input…” 2 次；说明句 “You can learn more about how ChatGPT uses connected apps here”、“Run npm install @cursor/sdk to get started” 也成了卡。
- 建议：按信号单独成卡（新模型、命名功能、默认开启、价格、弃用、GA）；其余条目每个 Release 合成一张 “Minor changes”；摘要卡标题带上前两项（“v2.1.316 · Apps: pooled group budgets, layered managed policy +5”）；小标题补母公告名（“Agent SDK: Evals”）；说明句并入母卡，套餐特性列表并入套餐卡。

### C3【中】标题

24.6% 以“…”截断；Claude Code 独立卡 68% 以 Added / Improved / Changed 开头；51 个 “VSCode Added …”（原文 `[VSCode]` 前缀被拍平）；144 个不超过 2 个词。建议规则改写（`[VSCode] Added X` → `VS Code: X`、去掉 changelog 动词），长标题由 LLM 提议并校验“≤ 90 字符且实词出自原文”，同样走缓存。

### C4【中】卡片页附属区块信息量低

2,550 张卡的 Related 只显示“最早的同主题条目”，只指向 24 个目标；264 张指向 Cursor 2023 年 nightly 的 “Agents, new docs”（原文 “agents, which we aren't releasing”），266 张指向同一张 ChatGPT 插件卡。Nearby 按日期取跨产品相邻卡，关联很弱。建议改为“本产品在该主题的上一条 / 下一条”，并移到构建期渲染（见 4.6）。

### C5【中】策展叙事：事实准确，选材偏弱、已过时

- Agent Mode 摘要的 Claude Code 段跳过 auto mode 与 dynamic workflows；Pricing Model 中 Claude Code 的关键节点是 “Renamed 'extra usage' to 'usage credits'”。
- 引用的最新日期为 10-09；Claude Code 的 scope 句仍写 “the last two weeks”。首页主推两个主题的 scope 句各 70 多词，约占全文 40%。
- PR #15 已整体批准（B6 通过），但复核包 13 个“判定：”为空，`editorial.yaml` 仍标 `awaiting-human-acceptance`。
- About 首段 “Every record is reviewed before it is published” 措辞过强：日更 50 多张卡，滚动 PR 半数被关闭。
- 建议每月刷新；scope 句不超过 35 词；Era 的 “present” 区间由代码计算。

### C6【低】待审积压与引文保真

- 63 条待审中 61 条为 no_match，主因是别名按字面匹配（code-review 匹配不到 “code reviews”，pull-request 匹配不到 “PRs”），加词形归一即可解决大半。Scheduled tasks 卡在待审，使 ChatGPT 第 4 个 Era 的代表 Release 没有卡。
- Quartz 默认的 SmartyPants 把引文中的 `--fixtures-dir` 渲染为 `—fixtures-dir`（9 张卡），`<pr-url>` 一类占位符被当作 HTML 标签吞掉（3 张卡）。

## 3. UI / 前端

1. **【高】线上图标与分享图 404。** 所有页面引用的 `static/icon.png`、`static/og-image.png` 在线上均 404。根因：`.gitignore` 含 `quartz`，Quartz 的 Static 插件用 `globby({ gitignore: true })` 收集 `quartz/static`，结果一个文件都不输出（node 实测：开启 gitignore 0 个，关闭 4 个）。
2. **【中】手机端横向溢出。** agent-mode 主题页在 390 px 宽度下实际 458 px，原因是关键节点表中 `CLAUDE_CODE_ENABLE_AUTO_MODE` 一类长串不可断行。设计评审 U9 的手机实测未做。
3. **【中】搜索索引大且有噪声。** `contentIndex.json` 原始 10.3 MB，gzip 传输 1.5 MB，卡片占 7.6 MB；每张卡的 “Also in this release / Nearby / Related” 进入索引，搜 “Channels” 会命中只是列出它的 “Evals”。
4. **【低】** 月份按时间倒序；主题页去掉图谱或限制 Backlinks；隐藏标签。

## 4. 代码设计

1. **【高】没有显式数据模型。** `_scripts` 中 191 处 `dict[str, Any]`，1 个 dataclass；卡片 schema 分散在 5 处（`extract.py`、`validate.py`、`history.py`、`writer.py`、`publication_filter.ts`）；活动卡的 `record` 有 13 种字段组合，历史记录从不重新校验。建议 `models.py` + `schema_version`，加载时统一校验与迁移。
2. **【高】原文未入库，身份与分组规则耦合。** Release 正文在落盘前丢弃，规则一变只能依赖上游重抓，也无法检测改稿。`card_id` = release + 全部引文的哈希；生产每天全量对账（`_scripts/operations.py:110,191`），上游每改一次稿，旧卡被退役、链接 404。31% 的 Changes 文件（1,257 / 4,024）已 superseded，没有重定向。建议提交 `data/releases/*.jsonl`（正文 + sha，约 1.8 MB）、以“行”为稳定身份、退役卡写入 `aliases` 指向继任者（AliasRedirects 已启用）。
3. **【高】`human_overrides` 写进了文档但没有实现。** README 第 102、116 行与 `docs/style-guide.md` 第 71 行让编辑把更正写进 `human_overrides`，`_scripts` 中没有任何代码读取它，更正会被静默忽略。同类：`evolves_from` 恒为空；`impact` 启发式未被使用，却让 572 张卡带上 `ai_generated: true`。
4. **【中】writer.py 过大、耦合重。** 2,351 行，`write_run` 312 行（`_scripts/writer.py:2026`）；同进程内阶段间靠 JSON 文件交接；`history.py` 反向依赖 writer；`publication.py:10` 运行时加载 `tests/manual/`。建议拆为 `vault/ownership`、`vault/store`、`render/pages/*`、`curation`，阶段间改为内存契约。
5. **【中】内容知识写死在代码里。** 主题 slug 与 226 条语义短语在 `extract.py`；About 中的数字是手抄常量；`sources.yaml` 的 `silence_window`、`language`、`backfill` 从未被读取；`silence_monitor.py` 有两个含义不同的 baseline。建议规则移入 `themes.yaml` 并加显式优先级、文案数字插值、FeedAdapter 注册表。
6. **【中】导航内容写进每个 Markdown 文件。** 一次日更新增 52 张卡、改动 124 个文件；一次格式迁移混入日更 PR 时达 1,006 个文件。建议 Markdown 只存事实，导航区块用 Quartz 组件在构建期渲染（同时解决搜索噪声）。
7. **【低】测试与工具链。** `test_writer.py` 有 99 处字符串字面量断言；CI 没有 ruff / pyright / tsc；Quartz 依赖为 `#v4` 分支引用（lock 已钉 `d25a6ea`）。建议模板测试改快照、package.json 钉 commit、加构建冒烟测试。

## 5. 运维 / CI / 流程

1. **【高】失败没人知道。** 16 次定时运行 14 次失败；PR #22 之后单源失败正常退出，只打 `::warning`（`_scripts/operations.py:264-266`）；浏览器安装步骤 `continue-on-error`（`.github/workflows/generate.yml:49-53`）。建议维护一个 “Pipeline health” issue：失败、持续降级、滚动 PR 积压时提醒，恢复后关闭。
2. **【高】ChatGPT 采集本质上在绕过站点的拒绝信号。** headless 浏览器 403 后改用有界面的 Chrome + Xvfb；首次正式自动采集混入客服组件生成的伪记录。部分成功模式已能让健康来源照常发布，建议默认关闭浏览器兜底。（OpenAI 条款适用性未核实。）
3. **【高】审核闭环流于形式。** 4 个滚动 PR 合并 2 个；“更新已有 PR”从未在生产执行；PR 正文只有计数。建议语义摘要 + 分级审核（PRD 11.1）：纯新增、零冲突批次自动合并或按周批量批准。
4. **【中】C1 检查会放行失败。** `_scripts/verify_schedule.py:21` 接受 `status=failed`，测试断言 7 次全部失败也通过。建议 C1 定义为连续 7 次 healthy 或带原因且不超过阈值的 degraded。
5. **【中】** 机器人 PR 每次触发两次 Quality，其中一次需手动放行（改用 GitHub App token 开 PR）；每天全量回填并重抓 Cursor 全部分页（改为每日增量、每周对账）。
6. **【中】文档过时、流程过重。** README 仍写“每个 Release 最多 5 张卡”与 run_pipeline 行为；运维手册与开发计划停在 10-15 左右。建议只在里程碑写验收记录，大证据文件存 Release 附件。
